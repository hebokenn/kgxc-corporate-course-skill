# Skill 发布流程

[返回主页](../README.md) · [完整版本历史](CHANGELOG.md)

维护本仓库的 Skill、发布包或主页时使用此流程。发布素材只包含可复用源码、说明和已授权公共资源；didi/pipi两套推荐参考与通用试听已获用户明确授权随包发布。其他私人课程原件、成片、个人参考录音、声音库与凭据保留在各自工程或本地配置中。

## 主页结构与内容维护

主页先帮助首次访问的人理解产品，再提供历史更新。顺序保持为：**首屏（一句大白话、演示入口、导航）→ 用途与交付 → 适用场景 → 核心能力及价值 → 制作流程 → 环境要求与局限 → 安装与使用 → 品牌定制 → 常见问题 → 相关文档与联系 → 版本更新**。具体章节名称可以随内容调整，**“版本更新”始终是 README 的最后一个内容章节**，不在其后追加安装、演示、使用指南或其他介绍。

撰写与修订主页时遵循以下要求：

- **首屏用大白话**：首屏用普通人能立刻听懂的一句话说明能交付什么，并给出直观演示入口，不堆叠工程或学术术语。
- **技术细节留在规范文档**：代码函数名、门禁枚举、像素坐标和 CLI 参数写在规范与技术文档中，不放主页正文。
- **流程图主简详折**：主流程图保持简洁横向以展示核心阶段与人工确认点，细节图（完整链路、协作时序、音画管线、增量渲染等）折叠收纳。
- **宣传用语有依据**：避免绝对化或夸张表述（如“电影级”“根治”“100%”“零剧透”“杜绝”等），收益与验证范围均以实际依据为准。
- **数据边界说准确**：区分“配音与渲染在本地完成、不调用云端 TTS”与“资料解析和写稿由你所用 AI 助手的模型处理”，不笼统宣称所有数据完全不出本机。
- **版本更新精简格式**：版本标题采用“版本号 · 日期 · ≤16 字主题”，每版只写 2–3 条面向用户的大白话要点；详细技术改动与验证记录留在 [CHANGELOG.md](CHANGELOG.md)。

每次新增或改变功能，都要同步修订前面的介绍，不能只在版本更新中记录：

- **使用场景**：谁在什么培训或制作任务中会用到，已有材料或前提是什么。
- **具体用法**：功能怎样参与制课流程，用户会看到、选择或得到什么；必要时给一个实际例子。
- **实际价值**：解决哪一类问题，怎样帮助讲解、理解、编辑、恢复或交付。收益以实际能力为依据，不虚构效率、学习效果或验证结论。
- **适用范围**：说明影响使用决策的环境、素材或验证范围，区分已有能力、技术验证与用户认可。

优先更新已有的场景和能力章节，保持读起来是一份连贯介绍；仅在确有新的能力类别时增加章节。介绍按当前能力写，不按版本号堆叠，也不把某次更新的样例、参数或章节数量固定为所有后续版本的模板。

版本更新放在主页末尾，按版本倒序概括变化及价值，详细记录、原始说明和验证链接保留在 [CHANGELOG.md](CHANGELOG.md)。整理历史时保留原记录，不把旧版本的默认值当成当前使用方式。

## 功能版本发布

1. 确认本次授权范围、当前源码版本及待发布变化，保留已有课程、个人配置和有效确认。
2. 更新源码及相关使用文档，并按上述要求把新功能的场景、具体用法和价值补入主页介绍；在最后的版本更新章节登记本版，补充完整历史与实际验证范围。
3. 完成与变化对应的验证，核对项目及安装副本；统一版本声明、安装包名称、主页下载入口和校验文件链接。
4. 使用 `python3 scripts/build_release.py` 构建可安装包与 `SHA256SUMS`。入口先强制检查主页结构；不通过时以非零状态退出，在清单写入、创建或覆盖 ZIP 及校验文件之前停止。修正后重新构建，并核对包清单、ZIP 和隔离安装行为。
5. 仅在上述检查与构建成功后，发布本次构建的源码、正式 tag、GitHub Release、版本安装包及校验文件；核对它们对应同一发布版本。构建失败不得继续上传，也不能拿上次遗留的包代替本次结果。
6. 检查线上主页、演示及文档链接，下载公共安装包并核对完整字节的 SHA-256 与 `SHA256SUMS`。大文件若分段下载，验证各段 `Content-Range` 并按顺序重组后计算哈希。
7. 分别报告源码与说明、项目及安装副本、安装包及公共下载的实际结果；尚未完成的部分明确列出。

仅调整主页文案、发布流程或维护指引时，提交并核对对应文档即可；不因此改动 Skill 功能版本、重建或替换既有版本的安装附件。

## 发布前主页检查清单

- [ ] 首屏用大白话说明输入、输出与适用对象，不堆术语，且提供演示入口与清晰导航。
- [ ] 主页不放函数名、门禁枚举或 CLI 参数，主流程图简洁横向且细节图已折叠。
- [ ] 宣传用语有实际依据、无绝对化表述，数据边界准确区分本地配音渲染与宿主模型处理资料。
- [ ] 本次每个面向用户的新功能或能力变化，在介绍中都有对应的场景、具体用法和价值；已有说明已按当前行为修订。
- [ ] 功能数量、素材范围与验证说明有实际依据，公开样片覆盖范围没有被扩大宣传。
- [ ] “版本更新”是 README 最后一个内容章节，标题符合“版本号 · 日期 · ≤16 字主题”，每版 2–3 条且与 [CHANGELOG.md](CHANGELOG.md) 对应，原有历史说明及验证链接保留。
- [ ] 当前安装版本、下载地址、校验文件、文档跳转及演示入口正确，线上页面已核对。

## 自动结构检查

可单独执行只读检查：

```sh
python3 scripts/check_readme.py
```

检查要求存在唯一的“版本更新”二级章节，并且后面没有同级或更高级章节。支持 Markdown 的 `## 标题` 和下划线式标题，忽略代码块及 HTML 注释中的示例标题；版本记录内部的三级及以下小标题可以保留。缺失、重复或顺序错误时返回状态码 `1`，提示行号及修改方法。

`build_release.py` 在任何打包写入前调用同一检查，不提供跳过选项。只有退出状态为 `0` 才能进入后续发布。回归验证使用临时目录：

```sh
python3 -B -m unittest discover -s tests -p 'test_release_readme.py' -v
```

场景和价值仍需结合本次实际变化逐项阅读，不能仅凭关键词、功能名称或结构检查通过代替。
