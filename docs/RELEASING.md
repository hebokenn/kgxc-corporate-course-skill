# Skill 发布流程

[返回主页](../README.md) · [完整版本历史](CHANGELOG.md)

维护本仓库的 Skill、发布包或主页时使用此流程。发布素材只包含可复用源码、说明和公共资源，私人课程原件、成片、个人参考录音、声音库与凭据保留在各自工程或本地配置中。

## 主页结构与内容维护

主页先帮助首次访问的人理解产品，再提供历史更新。顺序保持为：**用途与交付 → 适用场景 → 核心能力及价值 → 实际演示 → 制作流程 → 安装与使用 → 相关文档 → 版本更新**。具体章节名称可以随内容调整，**“版本更新”始终是 README 的最后一个内容章节**，不在其后追加安装、演示、使用指南或其他介绍。

每次新增或改变功能，都要同步修订前面的介绍，不能只在版本更新中记录：

- **使用场景**：谁在什么培训或制作任务中会用到，已有材料或前提是什么。
- **具体用法**：功能怎样参与制课流程，用户会看到、选择或得到什么；必要时给一个实际例子。
- **实际价值**：解决哪一类问题，怎样帮助讲解、理解、编辑、恢复或交付。收益以实际能力为依据，不虚构效率、学习效果或验证结论。
- **适用范围**：说明影响使用决策的环境、素材或验证范围，区分已有能力、技术验证与用户认可。

优先更新已有的场景和能力章节，保持读起来是一份连贯介绍；仅在确有新的能力类别时增加章节。介绍按当前能力写，不按版本号堆叠，也不把某次更新的样例、参数或章节数量固定为所有后续版本的模板。

版本更新放在主页末尾，按版本倒序概括变化及价值，详细记录、原始说明和验证链接保留在 [CHANGELOG.md](CHANGELOG.md)。整理历史时保留原记录，不把旧版本的默认值当成当前使用方式。

## 功能版本发布

1. 确认本次授权范围、当前源码版本及待发布变化，保留已有课程、个人配置和有效确认。
2. 更新源码及相关使用文档，并按上述要求把新功能的场景、具体用法和价值补入主页介绍；在最后的版本更新章节登记本版，补充完整历史与实际验证范围。
3. 完成与变化对应的验证，核对项目及安装副本；统一版本声明、安装包名称、主页下载入口和校验文件链接。
4. 使用 `python3 scripts/build_release.py` 构建可安装包与 `SHA256SUMS`，核对包清单、ZIP 和隔离安装行为。
5. 发布对应源码、正式 tag、GitHub Release、版本安装包及校验文件；核对它们对应同一发布版本。
6. 检查线上主页、演示及文档链接，下载公共安装包并核对完整字节的 SHA-256 与 `SHA256SUMS`。大文件若分段下载，验证各段 `Content-Range` 并按顺序重组后计算哈希。
7. 分别报告源码与说明、项目及安装副本、安装包及公共下载的实际结果；尚未完成的部分明确列出。

仅调整主页文案、发布流程或维护指引时，提交并核对对应文档即可；不因此改动 Skill 功能版本、重建或替换既有版本的安装附件。

## 发布前主页检查清单

- [ ] 首屏能说明这是做什么的、适合谁、需要什么资料、可以交付什么。
- [ ] 本次每个面向用户的新功能或能力变化，在介绍中都有对应的场景、具体用法和价值；已有说明已按当前行为修订。
- [ ] 功能数量、素材范围与验证说明有实际依据，公开样片覆盖范围没有被扩大宣传。
- [ ] “版本更新”是 README 最后一个内容章节；新增介绍、安装或演示均位于它之前。
- [ ] 主页版本概览与完整历史对应，原有历史说明及验证链接保留。
- [ ] 当前安装版本、下载地址、校验文件、文档跳转及演示入口正确，线上页面已核对。

结构顺序可以直接核对 README 标题；场景和价值需要结合本次实际变化逐项阅读，不能仅凭关键词、功能名称或自动检查通过代替。
